# 04 14日間の検証計画と次期ロードマップ

## 前提と制約
- 対象は1人・14日間。**機能の因果効果を証明することはできない**。目的は「使い続ける機能・直す機能・削る機能・次に試す機能」を決める材料を得ること。
- 2026-10-07までの累計（1,056分）から、日別実績や利用前の実行率は推定しない。比較のベースラインは存在しない。
- 毎日の追加入力はゼロ。データはアプリの通常操作で自動的に残る事実と、任意の1タップ回答のみ。

## 設計：ABA に近い交互比較（任意）
| 期間 | 表示 | 目的 |
|---|---|---|
| Day 1–7 | **プラン表示**（既定） | きっかけ・小さな一手・しおりを使う |
| Day 8–14 | **記録中心**（設定 → 支援の表示）※任意 | プラン要素がない場合と比べる |

- 記録中心に切り替えるのが負担なら、14日間プラン表示のままでもよい（比較はできないが、各指標の推移は見られる）。
- 各記録に `supportMode` が保存されるため、後でバックアップ（JSON）から期間ごとに集計できる。
- 7日では習慣の自動化（中央値59〜66日、Singh et al. 2024）は評価できない。**評価するのは「始めやすさ」と「再開」まで**。

## 指標（すべて端末内で自動、または任意回答）
| 指標 | 定義 | データ源 |
|---|---|---|
| **学習した日数** | 期間内で記録のある日の数（重複なし） | records.studyDate |
| **予定に対する実行率** | 予定の曜日のうち学習した日 ÷ 予定の日数（利用開始日以降） | settings.planDays × records |
| **開始までの時間** | アプリが画面に出てから開始までの秒数（30分超は除外） | records.openToStartSec |
| **再開状況** | 2日以上空いた後、何日目に再開したか／再開画面のどの選択肢で始めたか | 日付差、mode/fromBookmark |
| **次の一手の設定・実行** | しおりを残した割合／次回しおりから始めた割合 | bookmarkLeft, fromBookmark |
| 補助：学習時間・内容 | 分数・内容 | records |
| 補助：きっかけ通りの割合 | はい ÷ 回答数（任意回答） | cueFollowed |
| 補助：小さな一手の利用 | 回数、そこから目標を延長した回数（タイマー上の延長） | mode |
| 補助：操作負荷 | 週の見直しの「始めやすさ」1〜5（任意） | reviews.ease |
| 補助：使わなかった機能 | 期間中に一度も使わなかった機能 | 上記から |
| 補助：理解度（任意） | 記録のメモ欄に自由記述（例：仕訳があいまい） | records.note |

## スケジュール
- **Day 0**：プラン画面で きっかけ・しおり・小さな一手・予定の曜日 を決める（1〜2分）。バックアップを書き出す。
- **Day 1–14**：ふだん通り使う。終了時の「きっかけ通り？」は答えたいときだけ。
- **Day 7 / 14**：ホームの「週の見直し」で事実を見て1つだけ変える。
- **Day 14**：設定 → バックアップを書き出す（JSON）。下表で判断する。

## 判断基準（目安。1人のデータなので機械的に適用しない）
| 観察 | 判断 |
|---|---|
| しおりから始めた割合が高い／しおりを残す負担を感じない | **維持** |
| しおりをほとんど残さない | 終了画面の候補（続き・解き直し）を見直す → **改善** |
| きっかけ通り「ちがうタイミング」が多い | きっかけの選び方の案内を **改善**（時刻型との比較を次に検証） |
| 小さな一手を使った日が、使わなければゼロだった日に当たる | **維持** |
| 小さな一手ばかりで通常の一手が減った | 小さな一手の大きさを見直す（週の見直し） |
| 週の見直しを毎回「今週はしない」 | 頻度を下げる・自動提案をやめる → **改善／削除** |
| 2つの表示で学習日数・開始時間に差が見えない | プラン要素の重さを見直す。効果がないとは断定しない（7日×1人では判断不能） |

## 次期ロードマップ
| 段階 | 内容 | 前提 |
|---|---|---|
| P1 | 実行しやすかった条件の事実表示（曜日・時間帯ごとの学習回数。10件未満は表示しない） | 14日検証で記録が十分にたまったら |
| P1 | 14日検証用の集計画面（期間・表示モード別の指標を画面で確認） | 現在は JSON からの集計 |
| P1 | 簿記以外の習慣（学習対象を複数持つ） | 1つの学習で仕組みが使えると確認できたら |
| P2 | 端末間同期（PC・スマホ） | 認証・サーバーが必要。プライバシー設計とセット |
| P2 | 時刻型リマインダー（任意・オフが既定） | サーバー型 Web Push が必要。リマインダー依存の懸念（Stawarz 2015）を踏まえ、きっかけ型の補助に限る |
| P2 | カレンダー（.ics）への書き出し | 時刻型のきっかけを選んだ人向け |
| 保留 | 状況に応じた自動介入（JITAI）、AI による提案 | 根拠・データ・解決する課題が明確になるまで |
